# MPEG、脚本性能与帧率显示

本轮基于 `1.3.0 20260920.1059`。保留此前暂停菜单 GPU 提交、MPEG 原尺寸输出、
Ord Blocks 四条候选及 YUV 颜色修复。

最终构建：`1.3.0 20260920.1132`。EBOOT SHA256：
`ff1619ad5f29a02c9e693ad79138bf9cc00ef37a301b3105df177b6890fba0b0`。

## 依据与范围

最新 PPSSPP 日志中，STSTART 的三次关键帧处理分别为 34.265、32.893、32.424 ms，
对应完整视频阶段约 43.7–45.5 ms；同次 RGB 转换约 7.1 ms。关键帧计时包含
解析、读取和重建，并不能据此认定系数读取独占了多少时间。这份日志没有稳态
游戏峰值样本，游戏优化的工作量依据仍为此前 RCPLAY 的约 9309–10811 条指令慢 tick。

## 实现

- MPEG 增加 2 KiB 的八位查表，一次读取常见 DCT 系数及其符号，或块结束标记。
  首个非 intra 系数和后续系数使用不同表，保持 `1+sign` 与 `10`/`11+sign`
  的区别。只有已缓冲至少八位且完整码字及尾随位都落在该范围内时命中；长码、
  escape、短尾走原逻辑，不为查表额外读取文件。反量化、IDCT、颜色转换及
  音视频时间和跳帧策略不变，没有新增逐帧堆分配。
- VM 直接借用已缓存的 `ActionEntry`，消除每条指令的临时字符串复制和销毁。
  原来的拥有内容的复制 API 保留。每次迭代重新获取缓存项，所有 payload 都在
  宿主回调前求值或复制，避免递归扩容及场景重置后使用失效引用。

## 游戏中的 FPS 显示

用户报告游戏中 FPS 文字消失，读取的设置确认 `showFps=1`。原 FPS 和截图提示
仍由 CPU 直接写显存，在 GPU 缓存画面上存在与此前暂停菜单相同的提交差异。

现在把两种叠加层打包为小区域 ABGR 上传，通过同一条 GE 指令列表复制，统一
写回源缓存和同步。常见 FPS 面板仅上传约 1.6–2.5 KiB；带截图提示时约 49 KiB
以内。缓冲复用，退出游戏释放；不会为 FPS 每帧上传整个 480×272 菜单。

数字变窄时，游戏范围由正常重绘恢复；旧面板涉及黑边时另触发该页的 GE 清屏。
关闭 FPS、截图提示到期和暂停恢复也处理两页残影。计数仍只统计真正呈现的
新游戏/视频画面；截图继续排除 FPS 与通知。GPU 提交增加一次小指令列表同步，
其设备成本不包含在上面的核心阶段基准中。

## 验证与测量

两项候选均通过普通与 ASan/UBSan 对照。新增 20,966,008 个独立逐位 MPEG
系数用例，覆盖所有 17 位模式、八种对齐、首个/后续系数、短尾、escape 扩展、
流式补充读取和压缩缓冲上限；另保留整段解码、跳帧与流式读取回归。VM 完整
语义对照增至 378 次，并检查回调中清空 reader、递归扩大缓存、无效下标及复制
API 内容所有权；700268 次数值对照、257 次合成地图循环对照也通过。

以下比较使用完整的 1059 源码作为 before，与候选分别构建。相同主机、相同
`g++ -O3`，独立进程串行交替七轮，取计时段中位数。VM 与 MPEG 分开测量，
测量窗口没有本任务的并行编译或 sanitizer 作业。冻结的旧 0125 解释器只作为
兼容性 oracle，不作为本轮性能基线。

| 主机合成阶段 | 工作量 | 1059（微秒） | 当前（微秒） | 耗时变化 |
| --- | --- | ---: | ---: | ---: |
| VM，短文本 99 格循环 | 512 次 | 103247 | 90213 | −12.62% |
| VM，长文本同指令流 | 512 次 | 109626 | 97633 | −10.94% |
| MPEG，160×120 | 64 遍 / 4672 帧 | 242790 | 213039 | −12.25% |
| MPEG，352×288 | 16 遍 / 1568 帧 | 599692 | 483288 | −19.41% |

短文本变体将三个重复的 120/100/96 字节载荷改为 12/10/9 字节，两侧相同，
其余指令不变。两种 VM 负载的结果均为 sum=155232、99 个属性；每次执行
4864 条指令。长文本和短文本不能直接互比，也不能把长文本的分配成本假设为
所有游戏指令都有。

两个 MPEG 素材全部 28 次运行的帧数、完整 YUV/RGB/float PCM 摘要一致。MPEG
表格只计 `Video::decode`，不包含 RGB、PCM、摘要或文件加载。基准另将解码帧
转为 320×240 校验 RGB，原尺寸播放则由完整应用及原尺寸回归覆盖。RGB 和音频
阶段的中位波动小于 1%，不作为收益。PSP 反汇编确认常见系数命中路径没有
独立函数调用；escape/长码等仍调用原读取函数。

性能改动通过完整普通与 ASan/UBSan 的 AV、渲染、解释器、MPEG、图片及 MP3
检查；随后仅修改叠加层，最终 PSPSDK 全量构建，以及普通/sanitizer 的完整
应用显示、截图、原尺寸视频、帧调度、presenter 与核心摘要检查再次通过。
最终核心渲染摘要仍为 `8d63a40ac08ec6b1`。最终源码的 152 项构建输入与 PSP、
普通、sanitizer 三个目录逐项一致；核心源码与已经完成完整回归和测量的版本
相同。

新增独立 CPU/GPU 双页回归验证完整 FPS 数字字形、三种缩放、深浅主题、数字
缩窄、开关、暂停恢复、截图提示显示与消失，及截图排除叠加层。仅换回旧 FPS
直写实现的副本编译成功，并在首个 GPU 像素对照准确失败。

最终 EBOOT 在隔离 PPSSPP 1.20.4/Vulkan 中完成启动、GU/音频初始化和进入主页
的日志检查。后台 GPU 截图接口的限制仍见 [暂停显示验证](PAUSE-DISPLAY.md)；
本轮没有实际 PPSSPP 画面的截图验证或 PSP 真机测速。用户安装、设置、游戏
及存档未修改。

主机合成阶段耗时不等同游戏整体加速比例，也不能换算成 PSP 真机 FPS。
