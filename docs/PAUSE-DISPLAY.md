# 暂停菜单与 GPU 画面切换

本轮基于 `1.3.0 20260920.1000`，针对“部分画面按 □ 后暂停菜单不显示”的反馈。
构建为 `1.3.0 20260920.1059`，EBOOT SHA256：
`72c39b662067e8510c73d9979b31c395872216b3ff041dfd23018591631b908e`。

## 日志与修复依据

提供的 PPSSPP 日志对应 1000 构建，运行《Storm Wind》。NALOGO 视频为
352×240，使用原尺寸 GE 复制；STSTART 为 352×288，使用 GU 纹理缩放。
日志没有暂停切换记录，因此不能仅凭日志确定具体哪次按键没有显示菜单。

旧游戏路径通过 GE/GU 提交画面，而暂停、设置、截图浏览及加载页面在 CPU
直接写显存后交换页面。PPSSPP 使用独立 GPU 帧缓冲时，这些 CPU 写入可能没有
更新缓存中的可见画面。本轮消除这一混合提交路径，而不改游戏合成或 MPEG 解码。

- UI 在独立、16 字节对齐的 ABGR 缓冲中准备完整 480×272 页面，通过
  `sceGuCopyImage` 提交，等待 GE 完成后再交换双缓冲。
- 游戏与 UI 的上传缓冲独立；暂停期间仍能从保留的游戏画面截图。
- 恢复游戏及画布尺寸变化时，对需要清理的页同时执行 GE 黑色清屏，避免菜单
  留在游戏黑边里。稳定游戏帧不增加全屏清屏。
- UI 上传缓冲约 510 KiB，仅 UI 显示期间保留；进入游戏绘制即释放。加载回调
  若在该帧内重新分配，下一次游戏绘制释放。
- 日志新增 `pause: enter video=... source=... transfer=...` 与 `pause: resume`，
  便于后续区分视频/游戏路径及暂停操作。

## 验证与边界

PSPSDK 全量构建通过。普通及 ASan/UBSan 的完整应用 AV 测试、画面呈现测试
通过；新增独立 CPU/GPU 双页模型，CPU 写显存不会隐式更新 GPU 页，覆盖：

- 352×288 纹理与 352×240 原尺寸复制后的暂停，两页菜单逐像素校验；
- 方向选择、截图浏览及信息开关、游戏列表与设置往返；
- 暂停期间截图仍等于游戏画面，且不会改变当前可见页；
- 恢复后两页画面和周围黑边逐像素校验，暂停期间逻辑不推进。

两项负向反证均编译成功：只恢复旧 UI 直接显存写入时，在首个暂停菜单逐像素
检查失败；只禁用 GE 背景清理时，在恢复游戏的黑边检查失败。普通与 sanitizer
核心主机回归也通过，渲染摘要仍为 `8d63a40ac08ec6b1`。正式构建、普通测试和
sanitizer 目录中的全部 150 个构建输入均与同一份 SHA256 清单一致。

最终构建已在隔离的 PPSSPP 1.20.4 / Vulkan 中完成启动、GU/音频初始化和
进入主页的日志冒烟检查。未修改用户的 PPSSPP 安装、配置、游戏或存档。

后台调试器截图未能取得 GPU 图像：1.20.4 接口接受 CPU stepping 状态的请求，
但底层缓冲读取动作需要 GE stepping，返回 `Could not download output`。
因此本轮未用实际 PPSSPP 屏幕截图证明暂停显示恢复；独立页测试是主机模型，
不等同真实 GPU 验证。仍需用新 EBOOT 在原先出问题的片段确认，也未完成 PSP
真机验证。本轮不宣称 MPEG 或游戏帧率提升。
