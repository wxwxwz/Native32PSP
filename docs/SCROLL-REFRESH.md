# 同场景滚动与刷新尖峰优化

用户反馈游戏在同一场景内移动或滚动画面时，瞬时 FPS 会降到个位数。本轮针对新图片进入视口时的同步解码、屏外对象参与排序，以及 AUTO 对单次尖峰的后续反应进行优化，并补充能区分合成与图像解码的设备日志。改动归入 Unreleased，保留此前的 MPEG 优化。

用户同时反馈上一版 MPEG 播放约为 12 FPS。这是用户对上一版的观察，不是本轮滚动优化的真机测量，也不作为本轮性能提升的依据。后续已取得 `1.3.0 20260920.0036` 设备日志，用户仍报告约 8 FPS 的情况；新记录及继续细分核心尖峰的诊断工作见 [剩余低帧率与慢 tick 诊断](FRAME-SPIKES.md)。

## 排查依据

`NAV_ScreenMove` 更新画面偏移，不会重载场景或清空图像缓存。此前，完全在屏外的图片已经会跳过解码；滚动使其首次进入视口时，仍需在本次绘制中同步完成解码。旧路径先复制压缩图像块，再生成完整色度插值平面，最后扫描解码后的像素以统计透明边界，因此大量图片同时入屏可能集中产生工作。

已有设备日志 `tmp/game-smooth-device-before.log` 来自 `1.3.0 20260919.2224`。最后一次 `STPLAY10.SSL` 运行中，缓存图像数量从 15 增长到 170，记录的逐出次数为 0。这提供了运行期间持续遇到新图像的线索；它不能证明此次滚动尖峰的主因，也不能支持“缓存反复逐出”这一判断。旧 `logic_us` 同时包含核心逻辑与需要时的画面合成，无法单凭该项把耗时分配给脚本、解码或像素合成。

## 排序前剔除屏外对象

`Renderer::drawFrame` 在建立排序列表时，先以图像尺寸、对象坐标和画面偏移判断是否与视口相交。普通图片、电影帧图片和精灵替换图片均经过这一步，使大地图中完全在屏外的对象不再进入排序列表。

尺寸查询只读取缓存尺寸或资源头，不解码、不更新 LRU。实际图像查找、首次解码与 LRU 更新仍按最终绘制顺序执行；同深度对象之间的相对顺序保持一致。透明边界裁剪、透明洞处理以及完整不透明背景省略清屏的条件继续生效。

这项改动减少的是排序条目。对象遍历与必要的电影帧查询仍存在，不能把排序条目的减少直接换算成整帧耗时或 PSP FPS 的同比变化。

## 减少首次解码的复制与扫描

图像解码增加接收 `const u8*` 与长度的有界输入接口，原有 vector 接口保留。Reader 直接借用内容文件中的压缩图像范围，省去每次缓存缺失时复制压缩块的分配与内存传输。

YUV 解码保留原始 Y 平面与较小的 U/V 平面，以两条复用的色度行替代完整插值中间平面。零色度值仍先沿 Y 方向选择邻居，再沿 X 方向处理，保持原格式的替换顺序；奇数尺寸与边缘像素沿用旧解码结果。`Y=0` 继续表示透明。

YUV 转 RGB 时同时统计非零 alpha 像素的包围盒与完整不透明标记；ARGB RLE 解码则结合输出 run 更新这些信息。Reader 将融合生成的 metadata 与图像一起缓存，省去成功解码后再次扫描整张图。原有尺寸、长度检查及截断数据处理通过独立旧实现进行对照。

## AUTO 对单次尖峰的处理

此前，一次较慢的绘制可能在指数移动平均值中留下余波，后续正常绘制仍被反复计为超载，进一步降低绘制频率。本轮以当前绘制周期实际累计的耗时判断新的超载，周期包括其间跳过合成的追赶 tick；低于预算的周期可以偿还此前超出的耗时。

只有新的超预算周期才增加超载计数。尚未偿还的重复超载仍可触发降频，单次尖峰不再仅因平均值余波被计为多次超载。AUTO 保留每 1、2、3 次呈现机会绘制一次的间隔范围，以及用于恢复的平均耗时和迟滞条件；持续高负载仍会降低绘制频率。游戏逻辑与音频继续逐 tick 推进，MPEG 沿用自身的视频预算路径。

## 新增设备日志

运行日志新增一行：

```text
render: draw_us=<avg>/<max> image_decodes=<count> decode_total_us=<total> decode_peak_us=<peak>
```

| 字段 | 含义与统计范围 |
| --- | --- |
| `draw_us` | 本日志窗口内实际游戏画面合成的平均值与最大值，单位微秒；窗口输出后清零。跳过合成的 tick 和 MPEG 视频帧不作为游戏合成样本。 |
| `image_decodes` | 当前 Reader 内容的实际解码尝试累计次数，包括进入解码器后返回失败的尝试；缓存命中、负缓存命中和资源头检查即失败的请求不计入。 |
| `decode_total_us` | 当前内容中所有实际图像解码尝试的累计耗时，单位微秒，包括融合 metadata 的生成。 |
| `decode_peak_us` | 当前内容中单次实际图像解码尝试的最大耗时，单位微秒。 |

后三项随 Reader 设置新内容数据而清零，属于场景累计值，不随日志窗口输出清零。比较连续窗口时，应对次数与总耗时取差值；累计峰值只有出现更慢的解码时才增加。解码耗时在 PSP 构建中采集，普通主机替身不提供设备计时证据。

`draw_us` 包含合成过程中发生的首次解码，且属于原有 `logic_us` 的一部分，因此不能把这些嵌套耗时直接相加。结合 `resources:` 的缓存数量与逐出次数、`av:` 的 `render_period`，可进一步判断尖峰是否伴随新解码，以及绘制频率是否在尖峰之后恢复。

## 已完成的回归证据

图像解码已通过 794 个差分用例，与冻结的旧解码实现逐像素一致，融合 metadata 与独立 `imageDrawInfo` 扫描结果一致。覆盖 YUV run/literal、ARGB RLE、奇偶尺寸、透明像素、零色度替换顺序、未对齐输入、截断及错误数据，并检查 Reader 缓存中的结果。

滚动回归构造 4096 个地图 tile，在 192 帧中与独立旧绘制路径逐像素对照，包含缓存逐出与重新解码。像素、LRU 行为一致，输出摘要为 `771c7a1b35645133`。排序列表从原来的每帧 4098 项，缩小为平均 151 项、最大 160 项；这组数字描述合成用例的候选规模，不是真机计时结果。

AUTO 新增回归覆盖独立刷新尖峰、重复与持续超载、可偿还的短时负载、追赶 tick 的周期成本、计数上限及重置。完整普通 AV、核心渲染回归及两者的 ASan/UBSan 检查均通过；原核心摘要仍为 `8d63a40ac08ec6b1`，MPEG 的播放、AUTO 隔离、音频总量回归继续通过。

PSPSDK 已在全新目录全量重编译，构建日志无 warning/error。新 PBP 的 SHA-256 为 `fc72e9aaa973ba41fdcacb936ba4463c53e20dda4636d43299cdefb65a844aa0`。Reader 与 Emulator 新增诊断成员改变了类布局，不能只替换部分对象文件；构建与测试记录位于开发工作区 `tmp/scroll-refresh-verification/`。

## 解码基准与真机验证

独立基准比较“复制压缩块、旧解码、再次扫描 metadata”与“借用 span、新解码并融合 metadata”两条完整路径。素材包含 320×240 不透明及混合透明 YUV、64×64 YUV 精灵，以及 320×240 ARGB RLE。每组先验证新旧像素与 metadata，再按固定次数计时；摘要计算在计时范围之外，普通构建另统计 `new` 分配次数。

在 `psp/native32psp` 目录中，可先编译一次，再以独立进程交替测量：

```sh
sh tests/run-image-decode-bench.sh --build-only
tests/out/image-decode-bench --before
tests/out/image-decode-bench --after
```

| 图像 | 次数 | 改动前 | 改动后 | 耗时变化 | 每张图分配次数：前→后 |
| --- | ---: | ---: | ---: | ---: | ---: |

每轮像素及 metadata 摘要分别保持 `8182f6f9fbd607f8`、`16171157cdc97cf0`、`7f0ed219caf5bf47`、`20d6ca73a791cad9`。ARGB 合成素材包含重复像素 run，可直接更新边界，收益不能代表所有图像。

后续 [YUV 颜色修复](YUV-COLOR-FIX.md) 改变了相邻恢复后仍为零的色度处理；当前解码基准的两条路径均显式采用新颜色规则。上表耗时与 YUV 摘要保留为修复前历史记录，不是当前颜色修复构建的测量结果。

另对 4096 图块的 192 帧滚动场景交替测量 7 轮，单独比较排序前剔除：前后共享相同的新 Reader/解码器及类布局，仅替换 Renderer 实现。绘制总耗时中位数从 128577 降至 60208 微秒（-53.17%），每轮完整像素摘要均为 `771c7a1b35645133`。该结果不计测试参考绘制、摘要计算或显示上传；它与上述解码基准属于不同测量范围，不能将两项百分比相加。

原始记录为 `tmp/scroll-refresh-benchmark.log`，汇总为 `tmp/scroll-refresh-benchmark-summary.json`。这些都是主机上的合成素材结果。

后续 `20260920.0036` 设备日志显示，RCPLAY 在关闭跳帧时仍有约 102–123 ms 的核心 tick 峰值，而对应运行窗口的画面合成峰值约为 10–24 ms；详情及统计范围见 [剩余低帧率与慢 tick 诊断](FRAME-SPIKES.md)。这份记录不是相同场景的改动前后对照，尚不能量化本轮真机收益。主机差分与合成基准证明对应路径的行为和成本变化，不能换算成实际 PSP 帧率，也不能据此宣称用户报告的掉帧已经解决。
