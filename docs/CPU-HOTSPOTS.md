# 脚本数值处理与 MPEG 缩放颜色转换优化

0104 真机日志将 RCPLAY 的五次反复停顿定位到顶层 action 2246 调用链：核心总耗时 111–132 ms，其中 VM 为 100–120 ms，约占九成。实际脚本中，相机像素位置变化会引起 99 个地图格扫描和 22 个对象槽更新。这个工作量支持减少解释器的重复开销；本次保持脚本指令、分支、调用及游戏状态更新顺序。原始证据及统计限制见 [慢 tick 诊断](FRAME-SPIKES.md)。

同一日志中 NALOGO 的 RGB 转换约为每次 14.4 ms。本地对应 MPEG 的序列头确认视频为 352×288、25 FPS，目标游戏画布为 320×240，所以实际使用通用缩放路径。这解释了为什么此前针对原尺寸 2×2 色度共享的优化没有直接覆盖它。

## 游戏脚本

解释器原先用字符串保存栈值，每次数值运算均可能调用 `strtod`、软浮点转换和 `snprintf`。本次增加可精确验证的小整数路径：

- 可选正负号后有 1–9 位十进制数字、完整消费字符串时，使用 32 位累积解析。转整数直接返回；转 double 保留负零。
- 绝对值不超过 999999999、恰为整数且不是负零的 double，直接生成十进制文本。这一范围与原 `%.15g` 的结果一致。
- 完整 s64 整数格式化使用 32 位常见值路径；大值按十亿分块，处理最小负值时避免有符号溢出。
- 出栈改为移动字符串，减少复制，仍为每次递归调用保留独立栈和拥有内容的参数。

空白、尾缀、小数、指数、十六进制、超出快路径的长数字、嵌入 NUL、NaN/Inf 等继续走原解析；非整数、大数及负零继续走原 double 格式化。没有修改原有异常值转换到整数的既有未定义范围，也没有用 fast-math 放宽数值规则。

## MPEG 颜色转换

目标宽度不超过 512、源宽度不超过 65536，且纵向缩小不到两倍时，先计算精确的横向采样位置。相邻两条输出行若使用同一条源色度行，就在同一个平坦像素循环中共用 R/G/B 色度贡献，同时读取各自亮度并直接写入两行。不能配对的行单独处理；没有逐像素的区间循环或整行 RGB 贡献缓存。采样仍为 `floor(x * sourceWidth / outputWidth)`，两项绿色色度乘积仍在相加后只右移一次。

352×288 → 320×240 可以配对 96 组输出行，另有 48 条单行，每帧色度组合从 76800 次减少到 46080 次。辅助函数只使用 1 KiB 的列索引数组，不增加逐帧堆分配；原尺寸保留 2×2 色度共享，至少两倍纵向缩小及超出宽度范围时保留原通用处理，避免没有行共享收益时增加缓存开销。Cb/Cr 使用各自的行跨度，输出仍为原 ARGB 帧缓冲，呈现和截图契约不变。

本次保留 I/P/B 解码、MPEG 播放时间、音频、B 帧预算与跳帧策略。它减少缩放 RGB 转换成本，不宣称消除了 I 帧处理本身约 35–37 ms 的耗时。

- `run-vm-numeric.sh`：独立旧数值函数 oracle，覆盖边界、任意字符串/浮点位型、s64 分块、负零及异常格式；另有原创 99 格／22 槽合成循环对照。
