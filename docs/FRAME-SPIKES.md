# 剩余低帧率与慢 tick 诊断

用户反馈滚动优化后，游戏运行中仍会出现约 8 FPS，另有视频也会降到约 8 FPS。本页保留 0036 日志基线和 0104 新增诊断的统计边界，并在末节记录后续 0104 真机发现：RCPLAY 的反复尖峰主要落在脚本执行，NALOGO 的三个峰值均包含 I 帧处理与较高的 RGB 转换成本。诊断与后续 YUV 颜色修复均不代表这些卡顿已经消除。

## 设备记录与适用范围

本次依据为开发工作区的 `tmp/device-drop8-20260920.log`，启动标识是 `1.3.0 20260920.0036`。日志确认 CPU／总线实际频率为 `333/166` MHz；所列运行窗口均为 `skip=OFF`、`render_period=1`，采用 320×240 原尺寸、`GE-copy`、`sharp` 呈现。

这份记录包含 `NALOGO.mpg` 与后续游戏场景，重点分析 `RCPLAY.ssl` 加载后的六个连续窗口。它不是相同场景的改动前后对照，也没有记录能与用户所见 8 FPS 时刻逐一对应的慢 tick 标识。用户对其他视频的反馈不能仅用本份 `NALOGO.mpg` 日志代表。

关闭跳帧说明这些游戏窗口的低帧率不能归因于 AUTO 主动选择较大的呈现周期。`FrameClock` 的有限追帧仍然有效，MPEG 内部 B 帧预算也仍然有效；`OFF` 不表示每个过期画面或所有 B 帧都会被呈现。

## 本轮新增诊断的目的

本轮只增加耗时与工作量统计，保持原有逻辑、解码和跳帧策略。下一份记录需要把慢 tick 的主要阶段及当时工作量对应起来，区分游戏逻辑、影片帧处理、脚本执行、首次资源解码、音频与呈现成本；MPEG 也需要进一步区分处理阶段和 B 帧跳过原因。

统计在内存中累计，在原有五秒快照或视频窗口结束时集中打印，不逐 tick、逐指令写文件。VM 每条成功取出的指令只增加计数，只有顶层 `run` 的入口和出口读时钟，嵌套调用不重复累计墙钟耗时。

### 游戏快照

`game_peak`、`game_vm`、`game_sound` 三行全部来自该窗口内**同一次最慢的游戏 tick**，包括未绘制的追赶 tick。场景初始 tick、切换内容的 tick、视频 tick 不参与这个稳态峰值选择；原 `timing: logic_us` 仍统计它们。窗口可跨 SSL 场景，`scene` 是被选中 tick 的文件名；退出游戏或选择新游戏会清空峰值快照。

| 字段 | 统计边界 |
| --- | --- |
| `samples` / `over50ms` | 本窗口参与选择的游戏 tick 数／其中总耗时至少 50000 微秒的数量；`samples=0` 表示没有有效峰值样本。 |
| `at_us` / `tick` / `frame` | 被选中 tick 结束时的低 32 位系统微秒时钟、该场景 tick 计数、按键处理后主时间轴帧号。系统时钟约 71.6 分钟回绕一次，阶段计时使用无符号差值。 |
| `input` / `rendered` | 核心收到的按键位图／是否写入画面。方向左、右、上、下和 A、B、其他键依次为 1、2、4、8、16、32、64；描述传入按键，不等同于重复键处理后实际触发的事件。 |
| `total_us` | 应用调用 `Emulator::tick` 的总墙钟耗时，不含随后混音、音频入队和呈现。 |
| `timeline_us` / `movies_us` / `buttons_us` | 主时间轴加载及脚本、精灵动画帧推进及脚本/声音、按键处理及脚本。 |
| `pending_us` / `cheats_us` / `draw_us` | 待切内容处理、金手指应用、游戏合成。小量诊断与时钟推进成本不单列，所以各阶段之和不必精确等于总耗时。 |
| `game_vm` | 该 tick 的顶层脚本总耗时、含递归的调用数和指令数、最大深度；`slow_us/action/target` 是最慢顶层入口。target 最多保留 47 字节并替换换行；指令数包含成功取出的 End 指令。 |
| `game_sound` | 该 tick 的 `playSound` 尝试总耗时及调用数；最慢尝试的 `slow_us/value/format/bytes`，包括资源获取、复制、转换/播放启动。未知格式为 -1。它不包含随后普通混音，失败早退也计入调用数。 |

VM 和声音启动耗时嵌套在时间轴、动画或按键阶段内，不能与这些阶段再次相加。所有时间都是墙钟时间，也可能包含线程调度和同步等待，不能直接称为纯 CPU 指令耗时。`av` 行新增 `fps` 是最近一次显示帧率采样值，不是被选中慢 tick 的瞬时 FPS。

### MPEG 快照

每段视频独立统计，每 60 个 core tick 输出一次；正常结束、跳过、退出或切换内容会输出不足 60 tick 的剩余窗口。平均值按实际 `ticks` 计算，不再让短片残留值进入下一段视频。

`mpeg` 保留原有平均值及 `max_us`，增加窗口内音频解码帧数 `audio_frames`、推进的时间槽 `slots`、写入 RGB 次数 `rgb_frames` 和 B 跳过增量 `skipped_delta`。`skipped_b` 仍为当前影片累计值；RGB 写入数也不等于 PSP 实际显示帧数。

`mpeg_peak` 保存产生 `max_us` 的同一次 tick：包含 `audio_us`、`video_us`、该次音频帧数、视频 `decode_us/rgb_us`、decode 调用数与成功返回的时间槽数，以及呈现目标、调用者削减请求、内部预算削减请求、是否写入 RGB。`max_us` 仍从音频处理开始计到视频 advance 返回，不含视频初始化、日志写入和应用呈现。

`I/P/B/other` 的三元组分别表示 `decodePicture` 尝试次数、这些尝试总耗时和单次最大耗时。它们不是成功重建计数或显示帧数：一次 decode 可能处理多张参考图片，EOF 也可能只返回已有参考帧。B 跳过不计入图片尝试，而在 `skip` 三元组中单列次数、扫描总耗时、最大扫描耗时。图片计时包括内部资源读取与重建；外层起始码搜索、预取等落在总 decode 与子项之差内，不能将这段差值一概解释为 I/O。

呈现目标与预算标志描述本次调用的状态；内部为追赶较晚时间槽而跳 B 的逻辑仍存在，不能仅凭其中一个标志给所有跳帧分配原因。原音频、视频预算与呈现策略均未调整。

入口 2246 已用设备上的同一 `CHINESE/CRICH/RCPLAY.ssl` 静态解析核对（4087080 字节，SHA256 `ef21848a326d44f72ae613902f15516918153b108225571ac847ad6f0ea5469c`）：入口按游戏状态调度玩家/NPC模块，尾部调用 `CAMER`。相机调用链为 `2246 → CAMER(frame 15 / action 17591) → CA_BUFFER(frame 16 / action 18222) → BL_FIDX(frame 10 / action 14678)`。其中 Call 的参数是帧号，通过该帧的动作再进入 action，不是直接的动作索引。

`CA_BUFFER` 只要发现相机像素坐标改变，就先清理 22 个激活标记，遍历 9×11=99 个地图格，读取地图字符串、查地块状态并设置对象坐标和动画；之后再遍历 22 个对象槽，更新可见性及相对相机的位置。即使未跨越 32 像素的地图格边界，也会走这套刷新。这个循环和四层调用链与“同场景移动/滚动触发”及日志工作量相符，是明确的后续优化候选；目前没有嵌套函数级计时，仍不能断言整个 VM 峰值都来自它。优化应保持脚本语义，优先检查通用解释器中重复的数值/字符串转换、变量和对象访问；不能仅跳过游戏脚本刷新来换帧率。

I 帧处理是 `decodePicture` 墙钟时间，包含内部读取与重建；总 decode 与它的 8.720–16.143 ms 差额仍包含外层搜码、预取、调度等未细分工作，不能一概当作 I/O。每次真实 RGB 转换约 14.3–14.8 ms，原约 6–7 ms 的均值按全部 core tick 摊薄，低估了实际转换帧的成本。应用后续画面准备/呈现还在这些总计之外。三个峰值的 caller/budget reduce 均为 0，没有同时重建多个图片；这份记录支持继续优化 I 帧处理与颜色转换，不支持把全部慢帧归因于主动跳帧，也不能代表尚未记录的其他 MPEG 片段。
